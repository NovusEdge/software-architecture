# Security basics for architecture

The security properties that are decided by architecture rather than by code review: how much each credential can do, whether network location grants trust, whether a built artefact can be traced to reviewed source, and how secrets are stored and rotated.

Markers: [V] verified on the fetched page, with URL and fetch date; [U] not verified on a primary page; [I] inference by the author of this file. "(extraction)" means the quote came through a summarising fetch tool; re-open the page before quoting it in a decision.

## Least privilege

**Claim.** Give every user, service and process only the access it needs for its task, scoped as narrowly in resources and time as people will actually maintain.

**Why it holds.** Credentials leak or get misused eventually: through a log line, a compromised dependency, a stolen laptop, a bug that lets one tenant act as another. The damage is bounded by what the credential could do. A worker that only needs to read one bucket and holds a project-wide admin key turns a bug in that worker into control of the whole project; with a read-only key for one bucket, the same bug leaks one bucket [I].

**When it does not apply.** Permissions so fine-grained that nobody can maintain them lead people to share one broad credential to get work done, which is worse. Aim for the narrowest scope the team will keep correct, and review grants on a schedule.

**Sources.**
- [V] NIST CSRC Glossary, "least privilege" (from CNSSI 4009-2022): "A security principle that a system should restrict the access privileges of users (or processes acting on behalf of users) to the minimum necessary to accomplish assigned tasks." https://csrc.nist.gov/glossary/term/least_privilege (fetched 2026-10-07)

**Reviewer checks.**
- For each credential: who holds it, what is the least it could do, how long does it live, and how is it rotated and revoked?
- Can any component that runs untrusted or user-influenced code reach credentials, data or control planes beyond its own task?
- Is any credential shared between services or environments?

## Do not trust the network: authenticate and authorise every request

**Claim.** Treat an internal network as no safer than the internet. Grant access based on authenticated identity (of user, device and service) and authorise it at each service, rather than trusting requests because of where they come from.

**Why it holds.** Perimeter trust makes any foothold inside the network a foothold everywhere. If internal services accept unauthenticated calls because "only our own services can reach them", one compromised container, one misconfigured firewall rule or one server-side request forgery bug gives the attacker the whole internal API. If every service checks the caller's identity and permission, the foothold gets only what that one identity could do. Google's BeyondCorp applied this to employee access, removing the privileged corporate network entirely.

**When it does not apply.** BeyondCorp was designed for employee access at large scale with managed devices. For a small cloud system, the transferable parts are: authenticate service-to-service calls, authorise at each service, and do not rely on network location alone [I]. Network segmentation is still useful as an additional layer; the rule is not to rely on it alone.

**Sources.**
- [V] Rory Ward and Betsy Beyer, "BeyondCorp: A New Approach to Enterprise Security", ;login: (December 2014): "one should assume that an internal network is as fraught with danger as the public Internet"; BeyondCorp "dispenses with a privileged corporate network. Instead, access depends solely on device and user credentials, regardless of a user's network location"; "All access to enterprise resources is fully authenticated, fully authorized, and fully encrypted based upon device state and user credentials." https://www.usenix.org/system/files/login/articles/login_dec14_02_ward.pdf (fetched 2026-10-07)

**Reviewer checks.**
- Is any service trusted because it is on an internal network or behind a VPN?
- Do services authenticate each other, and does each service authorise the specific action?
- Can a server-side request from one service reach metadata endpoints or admin interfaces of another?

## Make the path from source to artefact verifiable (SLSA)

**Claim.** Build artefacts on a controlled build platform from version-controlled source and generate provenance (which source, which builder, which steps) that consumers can verify. SLSA defines incremental levels for this.

**Why it holds.** The build is the path from reviewed source to running binary; whoever controls the build controls the product, regardless of how carefully the source was reviewed. A developer laptop that builds and pushes images directly means a compromised laptop ships code to production with nobody seeing a diff. Provenance generated by a hosted build platform lets the deploy step refuse any artefact that was not built from a commit on the protected branch.

**When it does not apply.** SLSA level 1 (a scripted build that generates provenance) is cheap; higher levels need hardened build platforms and are justified mainly for software others run [I]. SLSA does not cover code quality, malicious maintainers or trust in transitive dependencies. Systems that build untrusted content for users (CI services, code-generation platforms) have a different and larger problem: isolating the build workers from each other and from secrets matters more than provenance of the platform's own code [I].

**Sources.**
- [V] SLSA specification, "About SLSA" (v1.0 and v1.2): "SLSA is a set of incrementally adoptable guidelines for supply chain security, established by industry consensus." It addresses source modification after review, artefacts not built by the expected platform, and threats to the build platform; v1.0 has a Build track with levels 1 to 3; v1.2 (current on the fetch date) has Build and Source tracks; out of scope: code quality, malicious producers, transitive trust. https://slsa.dev/spec/v1.0/about and https://slsa.dev/spec/v1.2/about (fetched 2026-10-07)

**Reviewer checks.**
- Can you show which source commit and which builder produced each deployed artefact?
- Can anyone push an artefact to production that was not built by CI from a protected branch?
- Where the system builds or runs user-supplied or generated content, are those workers isolated from secrets and from each other?

## Centralise, scope and rotate secrets

**Claim.** Keep secrets in a central store with access control and audit, prefer short-lived and dynamically issued credentials, never commit secrets to source or write them to logs, and have a tested procedure for revoking and rotating a leaked secret.

**Why it holds.** A secret in a repository or a long-lived shared key has an unbounded lifetime and no record of who used it. Once it leaks, every copy (forks, CI caches, laptops, old images) must be found, and the only real fix is rotation, which nobody has practised. A central store with short-lived credentials bounds both: a leaked token expires within the hour, and the audit log shows where it was used. Durable systems that persist their inputs (workflow histories, event logs, queues) keep any secret passed through them for as long as they keep the data [I].

**When it does not apply.** A secret manager is itself a dependency: decide what running workloads do when it is unreachable (see static stability in [overload.md](overload.md)). Very short-lived credentials increase load on the issuer and the impact of its outages.

**Sources.**
- [V] OWASP Secrets Management Cheat Sheet: "Centralize the storage, provisioning, auditing, rotation and management of secrets"; prefer dynamic, short-lived credentials; no hard-coded secrets; audit access; encrypt in transit; have an incident process for revocation and rotation (extraction; only the first sentence was returned verbatim). https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html (fetched 2026-10-07)

**Reviewer checks.**
- Are secrets absent from the repository history, logs, workflow inputs, event payloads and error reports?
- What is the leak response: who can revoke what, within how many minutes, and has it been rehearsed?
- What happens to running workloads when the secret store is unreachable?
